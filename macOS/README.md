# ParaAir macOS client

Last updated: 2026-10-09

ParaAir embeds a real FSKit extension for macOS 26 and later and the `paraair` CLI helper. The extension implements Apple's `FSVolume.Operations`, `ReadWriteOperations`, and `OpenCloseOperations` protocols against `StreamDriveCore.Engine`. It lists metadata without reading contents, serves offset/length reads, and records writes in the engine's durable local journal. The existing R2 drive mounts through Apple's native API at `/Volumes/ParaAir` on macOS 27.2. Native eject/remount, byte-exact cached range reads, Finder bookmarks, listing and sidebar navigation pass. Previews and editing applications remain untested.

## Build

From the `ParaAir` directory:

```sh
scripts/build-juicefs.sh
scripts/build-app.sh
```

The second command generates `macOS/ParaAir.xcodeproj` from `project.yml`, builds the extension into the shared `.build/xcode` directory, and assembles `.build/xcode/Build/Products/Release/ParaAir.app` without running Launch Services registration. The host, extension and packaged CLI each include `libstreamdrive.dylib`. The CLI executable lives inside `Contents/Helpers/ParaAirCLI.app/Contents/MacOS/paraair`, giving it an independent bundle identity and provisioning profile. `Contents/Helpers/paraair` remains the compatibility entry point. `STREAMDRIVE_NATIVE_LIBRARY` selects an explicitly supplied native library. The build checks for at least 100 GiB free before starting Xcode, creates no simulators and never installs or registers the app. An ad-hoc signature verifies packaging and compilation; it does not establish deployable entitlement authorization. Internal module names, environment variables and the existing `StreamDrive` state directory keep their compatibility identities.

For a distribution build, supply the existing Developer ID certificate's SHA-1 fingerprint and three matching Developer ID provisioning profiles:

```sh
STREAMDRIVE_SIGN_IDENTITY=EXACT_40_CHARACTER_CERTIFICATE_SHA1 \
STREAMDRIVE_TEAM_ID=TEAMID \
STREAMDRIVE_APP_PROVISIONING_PROFILE=/path/to/app.provisionprofile \
STREAMDRIVE_EXTENSION_PROVISIONING_PROFILE=/path/to/extension.provisionprofile \
STREAMDRIVE_CLI_PROVISIONING_PROFILE=/path/to/cli.provisionprofile \
scripts/build-app.sh
```

Signing defaults to noninteractive mode and never silently falls back to password UI. When the developer explicitly permits the normal macOS signing-key authorization, set `STREAMDRIVE_SIGNING_MODE=interactive` for that build. This runs Apple's `codesign` in the login session, where macOS can remember authorization for the signing key. It does not change ParaAir's runtime credential policy: app, CLI and extension Keychain operations still suppress interaction, and denied background reads remain paused. Passwords are entered only by the user in macOS's authorization UI, never passed to the build script.

`prepare-signing.py` validates macOS platform, validity dates, Developer ID distribution, team, exact App IDs, certificate inclusion, shared Keychain authorization and the extension's FSKit entitlement before Xcode or private-key use. It snapshots the public profiles so embedding uses the validated bytes. Generated entitlements contain only the project capabilities and the validated application/team/shared-group identities. An ad-hoc build removes stale shared-group configuration and embedded profiles. The old single-profile signing configuration is insufficient and is rejected.

Silent signing requires a verified headless Security session. It must never unlock Keychain, change key ACLs or fall back to interactive signing. [Apple's session API](https://developer.apple.com/documentation/security/sessioncreate(_:_:)) documents inheritance across exec; Apple's [SecurityAgent source](https://github.com/apple-oss-distributions/Security/blob/db15acbe6a7f257a859ad9a3bb86097bfe0679d9/securityd/src/agentquery.cpp#L143) refuses UI without graphical access. That source snapshot is corroborating evidence, not a permanent `codesign --no-ui` contract.

The initial C launcher stopped before private-key access with status `100001`: direct `SessionCreate` calls require privilege through `setaudit_addr`, even outside the tool sandbox. It has been replaced by `scripts/codesign-without-ui.py`, using launchd's documented `SessionCreate` property on a temporary user job. Apple's Python runs in isolated mode at each layer. The child rechecks UID, a distinct valid session and zero attributes immediately before exec of Apple's `codesign`; denial has no interactive fallback. Every invocation has a unique job, a bounded timeout, matching completion evidence, and verified removal. The default noninteractive build uses this same route for its preflight and every Developer ID signature. Its live `--check-session` returned UID/EUID 501, a new session, flags 0 and exit 0; job removal was confirmed. Custom probe binaries stalled before `main` inside dyld, so they did not establish a usable session. No session check alone demonstrates access to the signing key. Evidence is `.runtime/launchd-session-probe-20261002/` and `.build/signing/jobs/835b696c06c64093ba7df856399c52a2/`.

Developer ID signing and notarization are the intended public distribution path. They are separate from local development: [Apple DTS discusses locally signed FSKit builds](https://developer.apple.com/forums/thread/831843), including the need to approve a new ad-hoc build again because its signing identity changes. Absence of a Developer ID identity does not by itself prove that local activation is impossible. Our ad-hoc bundle has passed signature and callback checks, but its activation, sandbox access and Finder behavior have not yet been validated.

No installer or script changes System Settings automatically. Building the app target directly in Xcode uses Xcode’s ordinary automatic Launch Services registration; the provided script avoids that step. Apple's sample runs its containing app, enables the filesystem extension in System Settings → General → Login Items & Extensions → File System Extensions, and then mounts a directory. The person enabling the extension does not need a developer account merely to use an already built app.

Keep the menu bar app running while using renewable cloud connections; quitting stops its renewal timer even if a volume remains mounted. Credentials remain in Keychain; drive profiles contain connection IDs. After registering the containing app and approving the extension, `paraair mount PROFILE` invokes the equivalent of:

```sh
/sbin/mount -F -t streamdrive -o nosuid,nodev,-p=PROFILE \
  "$HOME/Library/Application Support/StreamDrive" /path/to/empty-mountpoint
```

One Finder mount state directory must contain exactly one profile. The unary filesystem container and volume share the same deterministic identifier; mounting a multi-profile state directory fails with an explicit error.

After verifying the actual mount, the app attempts a Finder Favorites registration through the public `LSSharedFileList` API. Apple deprecated it in macOS 10.11, and automatic insertion is best effort. A persistent, app-owned marker records successful registration for each state-root/profile identity; removing that favorite is respected on future launches. **Add to Sidebar** explicitly retries registration. The app preserves existing favorites and does not rewrite Finder preferences or its private databases. If insertion fails, open the mounted volume and drag its icon into Favorites. Finder Settings → Sidebar controls Favorites and Locations visibility. This path and the resulting sidebar appearance still require a runtime check; support on every Mac is not established. See [Apple’s API](https://developer.apple.com/documentation/coreservices/klssharedfilelistfavoriteitems) and [sidebar instructions](https://support.apple.com/guide/mac-help/customize-the-finder-sidebar-on-mac-mchl83c9e8b8/mac).

The source directory is **ParaAir's state/configuration directory**, not a source data directory to mirror. FSKit passes it to the extension as a security-scoped `FSPathURLResource`. The extension holds scoped access until unloading. `-p` selects an existing profile. This also supports an explicitly selected development state directory without granting broad filesystem access or placing credentials in a mount URL. The CLI must use argument arrays and reject commas in mount option values because `mount -o` interprets commas.

A native library outside the app bundle must be inside that granted state directory. A local development backend must also live inside it. Remote JuiceFS data is accessed through the extension's network-client entitlement. The extension has no blanket disk-access entitlement. Profiles with a `credentialID` show a Credential button in the app. A native secure text field stores the authenticated metadata URI in the core's Keychain service without displaying it in logs or configuration. The app and sandbox extension have separate identities: validate Keychain access under the actual distribution signature before deployment. ## Alternative Finder integration

FSKit is not the only Apple interface that can stream file content. A [File Provider domain](https://developer.apple.com/documentation/fileprovider/synchronizing-files-using-file-provider-extensions) represents a native Finder sidebar location, and [`NSFileProviderPartialContentFetching`](https://developer.apple.com/documentation/fileprovider/nsfileproviderpartialcontentfetching) supports requested ranges. Apple documents that POSIX partial reads can use this path, while whole-file cloning or file-coordinated reads request the full file. File Provider is therefore a supported alternative to evaluate for simpler Finder onboarding; it cannot be assumed to preserve bounded downloads for every application. Adopting it would require a separate extension adapter, version-consistent range delivery, system-managed local-file accounting and runtime validation. It is not implemented in this FSKit build, and the existing R2 connection and storage data should be retained during any future evaluation.

## Filesystem behavior

- The engine owns cache, pinning, pending data and process locking. FSKit operations run on a serial queue to maintain coherent item identities and namespace changes.
- Reads preserve the requested byte range. No mount, directory listing or metadata lookup triggers a full-file download.
- Writes acknowledge durable local journal data. A background timer attempts uploads every two seconds. Explicit synchronization waits for remote completion and returns the backend error when remote completion fails.
- A forced unmount or process termination may leave pending data. The core's persistent journal remains for restart; neither deactivation nor cache eviction deletes it.
- The reported allocated size comes from the engine's per-file local storage accounting. Remote logical size remains separate. Unknown S3 capacity is advertised as unknown, rather than an invented disk size.
- Hard links, symlinks, extended attributes, BSD flags and chmod/chown are not yet implemented. Capability flags disclose these limits; unimplemented link operations return `ENOTSUP` and unsupported set-attribute fields remain unconsumed. Applications requiring those features need validation before real use.
- Active item identifiers stay stable across the engine’s atomic uploads. Replaced or removed items become tombstones until FSKit releases them; stale item operations return `ESTALE` instead of accessing a new file at the old path. FSKit’s open-unlink emulation is enabled, but full POSIX behavior for applications holding files open across external replacements requires runtime validation.
- Directory enumeration uses bounded snapshots and opaque cookies. Expired snapshots fail with FSKit's invalid-cookie error so clients can retry.

Compilation alone does not validate Finder behavior. On a signed, enabled installation, run the project's acceptance workflow against a disposable profile, then verify Finder listing, JPEG/PDF/video Quick Look, video seek bytes, offline pinned reads, pending-write restart recovery, atomic rename, concurrent-writer conflicts and unmount with a failed upload.
